HTTP/HTTPS/TLS Network Security Analyzer

Academic laboratory investigation of transport-layer cryptographic protection, packet sniffing vulnerabilities, and TLS handshake protocols.
Network Security Lab

In standard computer networks, Hypertext Transfer Protocol (HTTP) transmits application payloads without encryption over TCP port 80, leaving credentials and session cookies exposed to passive packet interception. Conversely, HTTPS establishes a Transport Layer Security (TLS) cryptographic tunnel over port 443, ensuring confidentiality, authentication, and cryptographic integrity. This project visualizes these mechanisms through interactive network topologies and packet analysis.

Transmits request URIs, headers, and payload data as raw ASCII text. Vulnerable to MITM interception.
Secured HTTPS
Port 443 Protected

Comprehensive Technical Comparison: HTTP vs HTTPS

An evaluation of transport encryption, security guarantees, and vulnerability profiles.
Security Matrix

The fundamental flaw of the unadorned HTTP protocol is its lack of a security layer. HTTP assumes an inherently trusted communication channel, transmitting all application data as cleartext ASCII octets. HTTPS solves this by inserting the Transport Layer Security (TLS) protocol directly between the Application Layer (HTTP) and the Transport Layer (TCP).

Why HTTP Alone Cannot Provide Transport Encryption

RFC Standards Context

As defined in RFC 2616 / RFC 7230, HTTP is strictly a stateless application-layer request-response protocol designed to transfer hypertext documents. It contains no native primitives for key agreement, cipher suite negotiation, or message integrity checks.

By layering HTTP over TLS (defined in RFC 2818 for HTTPS and RFC 8446 for TLS 1.3), the application benefits from transparent transport encryption without requiring changes to HTTP methods (GET, POST, PUT) or header semantics. The browser sends normal HTTP requests, but the underlying TLS record layer encrypts each frame before handing it down to the operating system's TCP socket.

TLS 1.3 / 1.2 Cryptographic Handshake Architecture

An educational dissection of how asymmetric public-key cryptography establishes shared symmetric session keys.
Interactive Flow

Before any encrypted web application data can be transmitted over port 443, the client and server must execute a TLS Handshake. This process accomplishes three core security goals: (1) Parameter Negotiation (agreeing on ciphers), (2) Authentication (verifying the server's identity via digital certificates), and (3) Key Derivation (generating identical symmetric session keys using Diffie-Hellman).

Note for College Viva: Exact handshake packet sequences vary by version. TLS 1.2 requires 2 Round-Trip Times (2-RTT) with separate Key Exchange messages, while modern TLS 1.3 optimizes this to 1-RTT by including key shares directly in the Client Hello.

Project Overview & Academic Specifications

Course: Computer Networks & Cryptography Security Laboratory
Version 1.0 (Phase 1)

Project Title: HTTP/HTTPS/TLS Network Security Analyzer
Focus Area: Transport Layer Security, Cryptographic Key Agreement, Protocol Vulnerability Analysis, Packet Sniffing Defense.

This project was created to evaluate the stark security contrast between legacy plaintext protocols (HTTP) and cryptographically secured communication tunnels (HTTPS via TLS 1.2 and 1.3). By analyzing protocol frame structures in Wireshark and simulating network traversal across switches, routers, and firewalls, this tool provides students and educators with an intuitive, interactive platform for cybersecurity demonstrations.

Key Learning Outcomes

Curriculum Aligned
  • Understand the vulnerabilities of unencrypted application traffic on port 80 to Man-in-the-Middle (MITM) sniffing.
  • Analyze the cryptographic handshake of TLS, including Diffie-Hellman ephemeral key derivation and symmetric cipher setup.
  • Examine X.509 Public Key Infrastructure (PKI) certificates and server identity authentication.
  • Interpret real Wireshark protocol dissections, display filters, and packet byte dumps.
  • Model network communication flows using Cisco Packet Tracer-style topology concepts.
